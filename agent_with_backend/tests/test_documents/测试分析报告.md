# 测试分析报告（GB8567—88）

## 1 引言

### 1.1 编写目的

本报告记录 ROS2 智能药品拣选系统于 2026 年 6 月 6 日执行的项目集成测试结果，评价认证授权、智能筛查、药品库存、医生审批、订单下发和 ROS 状态接口之间的协作情况，并为后续缺陷修复和真实 ROS2/Unity 联调提供依据。

预期读者为项目开发人员、测试人员、ROS2 集成人员及项目负责人。

### 1.2 背景

- **系统名称**：ROS2 智能药品拣选系统
- **被测主体**：`agent_with_backend` Flask 后端及其 SQLite、认证、筛查、审批、订单和 ROS 集成模块
- **主要用户**：患者、医生、药房管理员及系统运维人员
- **测试环境**：Windows，Python 3.10.11，pytest 9.0.3，SQLite 临时数据库
- **执行时间**：2026-06-06 23:00 至 23:26（UTC+08:00）

本次测试通过 Flask 测试客户端调用真实控制器和认证中间件，通过临时 SQLite 数据库验证持久化与事务。ROS2 消息发布使用 Mock，未连接真实 ROS2 节点、Unity 仿真或机器人；LLM 外部服务未调用。因此后端业务集成结论有效，但不代表真实机器人链路、网络性能和 LLM 输出质量已验收。

## 3 测试结果及发现

### 3.1 新增集成测试

执行命令：

```powershell
python -m pytest tests\integration -q --tb=short --disable-warnings `
  --cov=api --cov=auth --cov=screening --cov=database `
  --cov=ros_integration --cov-report=term-missing
```

结果：**8 passed，2 xfailed，0 unexpected failed**，耗时 14.72 秒。所选相关模块语句覆盖率为 **34%**。

关键验证结果：

- 注册、JWT 校验、刷新及注销后的刷新令牌撤销正常。
- 患者可执行症状标准化和筛查，筛查历史成功写入数据库。
- 患者不能访问库存管理或执行医生审批，管理员可读取审计日志。
- 审批通过后库存由 10 减至 8，生成订单任务并调用 ROS 发布接口。
- 批量订单中任一药品库存不足时，全部库存、订单和流水均不变。
- 直接订单正确写入 `order_log` 和 `inventory_transactions`。
- ROS 状态存储中的小车、任务和药柜数据可由 HTTP API 查询。

### 3.2 后端全量测试

执行命令：

```powershell
python -m pytest tests -q --tb=short --disable-warnings
```

结果：**259 passed，2 xfailed，7 failed**，耗时 53.87 秒。

7 个失败均属于 ROS 集成测试：

- 2 项：最新 ROS 状态被误判为离线。
- 5 项：无 ROS2 运行库时，`QoSProfile`、`String` 等替身不完整，发布器初始化或旧版消息创建失败。
- 测试结束时还观察到 `atexit` 使用字符串测试替身执行 `shutdown()`、`destroy_node()` 的异常。

### 3.3 仓库根级测试

仓库根目录 `tests/thought_logging` 在收集阶段出现 6 个错误，全部源于导入路径仍指向已不存在的 `agent_with_backend.P1.thought_logging`。当前实际模块位于 `agent_with_backend/thought_logging`，因此这些测试未能执行。

ROS 工作区中的测试依赖 ROS2/ament 环境；Unity 目录未提供可由当前 pytest 环境自动执行的集成测试。本次未将其计为通过。

## 4 对软件功能的结论

### 4.1 认证与权限

#### 4.1.1 能力

注册、登录、令牌校验、刷新、注销、角色权限和审计日志可协同工作。患者、医生和管理员的关键权限边界得到验证。

#### 4.1.2 限制

未执行高并发会话、令牌过期等待、密钥轮换和渗透测试。

### 4.2 智能筛查

#### 4.2.1 能力

可将“头疼”“发烧”标准化为“头痛”“发热”，完成药品筛选、置信度排序和历史记录保存。

#### 4.2.2 限制

筛查药品仍来自 `ScreeningService.SAMPLE_DRUGS`，未与真实库存药品表统一；年龄和过敏过滤逻辑仍为待实现项。

### 4.3 审批、订单与库存

#### 4.3.1 能力

患者提交审批、医生审批、自动扣库、创建任务、患者确认完成的主流程可执行。直接订单具备事务原子性，并记录库存出库流水。

#### 4.3.2 限制

审批自动下单直接修改库存和订单表，未写入 `inventory_transactions`，造成审计链不完整。该问题已由严格 xfail 用例固定。

### 4.4 ROS 状态与任务接口

#### 4.4.1 能力

模拟订阅状态可经 API 查询；返回队列命令受库存更新权限保护；业务层可触发任务发布接口。

#### 4.4.2 限制

Python 3.10 环境中，末尾为 `Z` 的时间戳无法被当前 `datetime.fromisoformat` 调用解析，导致在线状态误判。无 ROS2 库时的发布器替身也不完整，尚未完成真实消息传输验证。

## 5 分析摘要

### 5.1 能力

本次测试证实后端核心跨模块流程基本可用：认证授权、筛查、审批、订单、库存和 ROS 状态 API 能在隔离数据库环境中协同运行。新增集成测试本身无意外失败，通过率为 100%（已知缺陷按 xfail 管理）。

### 5.2 缺陷和限制

| 编号 | 等级 | 缺陷或限制 | 影响 |
|---|---|---|---|
| DEF-INT-001 | P2 | 审批自动下单未写库存流水 | 审计记录不完整，影响库存追溯 |
| DEF-ROS-001 | P2 | `Z` 时间戳在 Python 3.10 下解析失败 | ROS 在线状态被误判为离线 |
| DEF-ROS-002 | P2 | 无 ROS2 环境时消息类型和 QoS 替身不完整 | ROS 发布器测试失败，降级能力不足 |
| DEF-ROS-003 | P3 | ROS 测试替身注册 `atexit` 后关闭异常 | 测试退出有异常日志，可能掩盖真实问题 |
| DEF-TEST-001 | P2 | 根级 thought_logging 测试引用已删除的 `P1` 包 | 6 个文件无法收集，形成测试盲区 |
| DEF-TEST-002 | P3 | 全局药品缓存与临时数据库生命周期不一致 | 特定测试顺序下可能读取旧库同 ID 数据 |

### 5.3 建议

1. 审批自动下单复用 `create_order_for_drug()`，统一库存扣减、订单和库存流水事务，优先级高，预计 0.5 人日。
2. ROS 时间戳统一使用 `datetime.fromisoformat(value.replace("Z", "+00:00"))`，优先级高，预计 0.25 人日。
3. 将 ROS 消息类型、QoS 和节点生命周期封装为可注入适配器，完善无 ROS2 环境测试替身，优先级高，预计 1 至 2 人日。
4. 将根级测试导入路径迁移到 `agent_with_backend.thought_logging`，优先级高，预计 0.5 人日。
5. 在所有临时数据库夹具前后清空药品缓存和审批/ROS 单例，优先级中，预计 0.5 人日。
6. 在 Ubuntu ROS2 环境中补做 ROS-TCP-Endpoint、Unity 和真实话题端到端测试。

### 5.4 评价

后端核心业务链路已达到“可继续联调”的阶段，但**尚不建议作为完整系统直接验收交付**。发布前至少应修复 DEF-INT-001、DEF-ROS-001、DEF-ROS-002 和 DEF-TEST-001，并在真实 ROS2/Unity 环境重新执行机器人任务发布、状态回传和异常恢复测试。
