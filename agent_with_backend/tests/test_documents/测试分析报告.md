# 测试分析报告

## 1 引言

### 1.1 编写目的

本报告记录 ROS2 智能药品拣选系统的自动化测试结果，评价 AI 医疗助手、认证授权、智能筛查、药品与库存、医生审批、订单流程及 ROS2 集成模块的当前质量，并为缺陷修复和后续 ROS2/Unity 联调提供依据。

预期读者为项目开发人员、测试人员、ROS2 集成人员及项目负责人。

### 1.2 被测对象

- **系统名称**：ROS2 智能药品拣选系统

- **测试范围**：`tests/` 下默认可发现的自动化测试，以及显式执行的 `test-full-integration.py`
- **未测试范围**：Unity、机器人硬件、安全渗透

## 3 测试结果及发现

### 3.1 测试1（UT-001：药品 API 基础操作单元测试）

本项测试对药品控制器的创建、删除、库存调整、药品查询、低库存查询和临期药品查询进行验证。

| 比较项目 | 动态输出要求 | 实际动态输出 | 比较结果 |
|---|---|---|---|
| 用例执行 | 所有单元测试均成功执行 | `6 passed, 12 warnings in 6.23s` | 功能用例全部通过 |
| 创建药品 | 返回成功结果，并在数据库中生成药品数据 | 创建用例通过，临时 SQLite 数据库中生成对应药品记录 | 符合要求 |
| 查询药品 | 返回与输入条件匹配的药品数据 | 普通查询、低库存和临期查询用例全部通过 | 符合要求 |
| 库存调整 | 输出调整后的库存数据，数据库同步更新 | 库存调整用例通过 | 符合要求 |
| 执行时间 | 单元测试执行时间小于 10 秒 | 6.23 秒 | 符合要求 |

**发现：**

1. 药品控制器的六项基础操作均得到预期动态输出，未发现功能失败。
2. 执行过程中产生 12 条 JWT 密钥长度警告。测试使用的 HMAC 密钥为 22 字节，低于 SHA-256 建议的 32 字节；该问题未影响本项功能结果，但应修正测试及部署配置。

### 3.2 测试2（IT-001～IT-005：API 集成测试）

本项测试覆盖认证生命周期、角色权限、智能筛查、筛查历史、药品与库存 API，以及不同模块之间的数据传递。

| 比较项目 | 动态输出要求 | 实际动态输出 | 比较结果 |
|---|---|---|---|
| 用例执行 | API 调用链路成功率不低于 95% | `8 passed, 2 xfailed, 20 warnings in 12.60s` | 无非预期失败，但有 2 项已知缺陷 |
| 认证生命周期 | 注册、登录、验证、刷新、注销输出正确，注销后刷新失败 | 对应请求依次返回成功；令牌注销后刷新请求返回 `401` | 符合要求 |
| 权限控制 | 患者、医生和管理员只能访问其权限范围内的接口 | 患者访问库存接口返回 `403`，患者审批操作返回 `403`，管理员可查询审计日志 | 符合要求 |
| 症状标准化 | “头疼”“发烧”转换为“头痛”“发热”，未知症状单独返回 | 输出包含标准症状 `头痛`、`发热`，并将“未知症状”列入未匹配项 | 符合要求 |

**发现：**

1. 认证、权限、筛查和历史记录之间的数据传递正确，主要 API 集成链路可用。
2. `test_approval_dispatch_writes_inventory_transaction` 为严格 xfail。实际输出表明审批自动下单会扣减库存，但没有生成 `inventory_transactions` 记录，库存审计链不完整，记为 DEF-INT-001。
3. `test_recent_ros_state_reports_connected` 为严格 xfail。最新 ROS 状态经 HTTP 查询时仍可能输出 `connected=false`，相关原因见 3.4。

### 3.3 测试3（E2E-001：完整用药流程测试）

本项测试验证患者提交审批、医生处理、库存扣减、订单生成、任务发布调用和患者确认完成之间的完整业务流程。

| 比较项目 | 动态输出要求 | 实际动态输出 | 比较结果 |
|---|---|---|---|
| 患者提交审批 | 返回审批编号并保存待审批数据 | 请求返回 `201`，生成 `approval_id` | 符合要求 |
| 医生待办查询 | 待审批列表中包含新生成的审批编号 | 查询返回 `200`，列表包含对应 `approval_id` | 符合要求 |
| 医生批准 | 审批状态更新并创建订单任务 | 请求返回 `200`，`order_created=true`，生成 `task_id` | 符合要求 |
| 库存变化 | 批准数量为 2 时，库存由 10 减少至 8 | 数据库实际库存为 8 | 符合要求 |
| 任务发布 | 发布函数接收正确的任务、药品和数量 | Mock 捕获输出为 `(task_id, drug_id, 2)` | 符合要求 |
| 流程完成 | 患者确认后审批状态变为 `completed` | 完成请求返回 `200`，最终状态为 `completed` | 符合要求 |
| 事务原子性 | 批量订单任一项目无效时全部回滚 | 库存分别保持 10 和 1，订单、库存流水及发布调用数量均为 0 | 符合要求 |
| 直接订单审计 | 扣库、订单和库存流水数据一致 | 库存由 6 变为 4；订单数量为 2；流水变化量为 `-2` | 符合要求 |

**发现：**

1. 患者、医生、库存、订单和任务发布调用之间的主业务链路能够完成，内部生成的审批编号和任务编号可在后续步骤继续使用。
2. 批量订单在库存不足时能够整体回滚，没有产生部分扣库或无效任务。
3. 直接订单能够生成库存流水，但审批自动下单未生成同类流水，因此两条下单路径的动态输出不一致。
4. 显式执行旧文件 `test-full-integration.py` 时得到 `2 passed`，但两个测试函数通过返回布尔值报告结果，pytest 同时输出 `PytestReturnNotNoneWarning`。该文件存在流程失败后仍被判为通过的风险，不能单独作为正式 E2E 验收依据。

### 3.4 测试4（E2E-004：ROS2 集成测试）

本项测试使用 Mock/替身验证 ROS 配置、节点管理、消息转换、状态存储、健康监控、错误处理、任务发布和返回队列命令。

| 比较项目 | 动态输出要求 | 实际动态输出 | 比较结果 |
|---|---|---|---|
| 独立测试集执行 | ROS2 集成用例成功率不低于 95% | `129 passed, 2 failed in 16.24s`，成功率 98.47% | 数量指标达到要求|
| 消息格式转换 | 药品、货架、任务和小车状态正确转换 | 消息适配相关测试全部通过 | 符合要求 |
| 错误与降级处理 | 发布异常产生重试或降级结果，系统不崩溃 | 错误处理和健康监控测试通过 | 符合 Mock 测试要求 |

**发现：**

1. `updated_at` 使用末尾为 `Z` 的时间格式，Python 3.10 的 `datetime.fromisoformat()` 无法直接解析；异常被忽略后，最新状态被错误输出为离线，记为 DEF-ROS-001。
2. 无 ROS2 环境时，测试将 `ROS2_AVAILABLE` 修改为 `True`，但没有同步提供 `QoSProfile`、`String` 等完整替身，分别产生 `NameError` 和 `TypeError`，记为 DEF-ROS-002、DEF-ROS-003。
3. ROS 测试单独执行时有 2 项失败，全量执行时扩展为 7 项失败，表明模块级标志、消息类型或单例没有在测试之间完整恢复，测试结果具有顺序依赖，记为 DEF-ROS-004。
4. 测试退出阶段出现替身对象没有 `shutdown()` 或 `destroy_node()` 的 `atexit` 异常。该异常未计入 pytest 失败数，但会干扰结果判读。
5. 本项仅验证 Mock/替身环境，尚未取得真实 ROS2 话题、ROS-TCP-Endpoint、Unity 或机器人产生的动态输出。

## 4 对软件功能的结论

### 4.1 认证与权限

注册、登录、刷新、注销、JWT 校验和角色权限测试通过，核心权限边界可用。但测试密钥长度不足，尚未执行令牌过期等待、密钥轮换、并发会话和渗透测试。

### 4.2 智能筛查与 Agent

症状标准化、药品筛选、历史记录，以及 Agent 的消息、记忆、工具和工作流基础能力通过测试。

### 4.3 药品、库存、审批与订单

药品 CRUD、查询、分类、库存调整和主要审批下单流程可执行，批量订单的事务原子性得到验证。但审批自动下单未生成库存流水。

### 4.4 ROS 状态与任务接口

配置、消息转换、错误处理和健康监控的大部分逻辑通过 Mock 测试。本次未验证真实 Unity 通信和故障恢复。

## 5 分析摘要

### 5.1 能力

经测试，本软件具有如下能力：
1. Agent 的消息模型、记忆压缩、待办管理、工具注册和工作流状态管理等功能完善；
2. 用户注册、登录、令牌刷新与注销、角色权限、筛查历史和关键 API 权限边界等功能完善；
3. 药品 CRUD、搜索、分页、批量导入、导出、分类和库存调整等功能完善。
4. 患者提交审批、医生审批、扣减库存、创建任务和患者确认完成的主要业务等功能完善。
5. ROS 配置、错误处理、健康监控、消息适配、节点管理等功能完善。

### 5.2 缺陷与限制汇总

| 编号 | 等级 | 缺陷或限制 | 建议 |
|---|---|---|---|
| DEF-ROS-001 | P2 | `Z` 时间戳解析失败，在线状态误判 | 解析前将 `Z` 转为 `+00:00`，并补充时区测试 |
| DEF-INT-001 | P2 | 审批自动下单未写库存流水 | 复用统一订单事务逻辑，保证库存、订单、流水原子提交 |
| DEF-ROS-002 | P2 | 无 ROS2 环境时 QoS 替身不完整 | 对 ROS 类型和 QoS 建立可注入适配层 |
| DEF-ROS-003 | P2 | 旧消息类型为空导致发布失败 | 测试中完整注入消息类，生产代码明确降级路径 |
| DEF-ROS-004 | P2 | ROS 测试存在顺序依赖 | 每个用例恢复模块级标志、单例和导入对象 |
| DEF-TEST-001 | P2 | 生产代码覆盖率仅 39% | 优先补齐订单、Agent、状态订阅和任务发布测试 |
| DEF-TEST-002 | P3 | E2E 文件未被默认发现且返回布尔值 | 重命名为 `test_full_integration.py` 并改用断言 |
| DEF-TEST-003 | P3 | ROS `atexit` 回调退出异常 | 隔离单例生命周期，避免注册重复回调并校验替身接口 |
| DEF-SEC-001 | P2 | JWT 测试密钥长度不足 | 使用至少 32 字节的测试与部署密钥 |
| DEF-ENV-001 | P3 | 缺少 `pytest-html`，虚拟环境跨平台不可用 | 完善开发依赖和 Windows/Linux 环境说明 |

### 5.3 建议

系统的 Agent 基础能力、认证授权、药品库存 API 和主要审批流程已具备继续开发与联调的基础。但仍存在 ROS 发布器测试与降级替身不完整、审批库存流水缺失等问题。

修复后应在相同 Python 3.10 环境重跑全部 268 项默认测试及显式 E2E 测试，并在 Ubuntu ROS2 Humble、ROS-TCP-Endpoint 和 Unity 环境补做真实消息端到端验证。
