## 1. 系统总体架构

## 3. 药品管理 API 设计 (api/)

### 3.1 设计原则

- **RESTful 风格**：资源路径 + HTTP 动词
- **统一响应格式**：`{code, message, data, meta}`
- **分页与筛选**：支持 `page`, `per_page`, `sort_by`, `order` 参数
- **输入验证**：统一的 validation 层守卫所有写入端点

### 3.2 控制器清单

| 控制器 | 注册前缀 | 端点数量 | 主要功能 |
|--------|----------|----------|----------|
| `health_controller` | `/api/health` | 2 | 系统健康检查、ROS2 状态 |
| `drug_controller` | `/api/drugs` | 10 | 药品 CRUD、库存调整、批量导入、导出、统计 |
| `order_controller` | `/api/orders` | 3 | 订单创建、列表、详情 |
| `approval_controller` | `/api/approvals` | 6 | 审批 CRUD、审批/驳回操作 |
| `category_controller` | `/api/categories` | 2 | 类别列表、创建 |
| `upload_controller` | `/api/upload` | 3 | 文件上传、下载、删除 |
| `ros_state_controller` | `/api/ros` | 7 | 车辆状态、任务状态、柜子状态 |

### 3.3 统一响应格式

```json
{
  "code": 200,
  "message": "success",
  "data": { ... },
  "meta": {
    "page": 1,
    "per_page": 20,
    "total": 100,
    "pages": 5
  }
}
```

### 3.4 错误码体系

系统统一使用以下错误码分类（参考 HTTP 状态码语义扩展）：

| 错误码范围 | 类别 | 说明 | 示例 |
|-----------|------|------|------|
| `200` | 成功 | 请求成功处理 | GET /api/drugs 返回 200 |
| `201` | 创建成功 | 资源创建成功 | POST /api/drugs 返回 201 |
| `400` | 请求错误 | 参数校验失败、格式错误 | `{"code": 400, "message": "price 必须为正数"}` |
| `401` | 未认证 | JWT 缺失或过期 | `{"code": 401, "message": "Token expired"}` |
| `403` | 无权限 | RBAC 权限不足 | `{"code": 403, "message": "Permission denied: delete:drug"}` |
| `404` | 资源不存在 | 未找到指定资源 | `{"code": 404, "message": "Drug not found"}` |
| `409` | 冲突 | 资源已存在、库存不足 | `{"code": 409, "message": "库存不足: 当前 2, 需求 5"}` |
| `422` | 不可处理 | 业务规则违反 | `{"code": 422, "message": "处方药需医生审批"}` |
| `429` | 频率限制 | 请求过频 | `{"code": 429, "message": "Too many requests"}` |
| `500` | 服务器错误 | 内部异常 | `{"code": 500, "message": "Internal server error"}` |
| `503` | 服务不可用 | ROS2 断开、LLM 超时 | `{"code": 503, "message": "ROS2 not connected"}` |

接口规范补充：

```
请求头:
  Authorization: Bearer <access_token>
  Content-Type: application/json

分页参数:
  ?page=1&per_page=20&sort_by=name&order=asc

错误响应体:
  {
    "code": 4xx,
    "message": "错误描述",
    "errors": [{"field": "price", "message": "必须为正数"}]
  }
```

## 5. 智能筛选系统设计 (screening/)

### 5.1 设计目标

- 根据患者症状描述，从 116+ 种药品中智能匹配推荐
- 支持多维度排序（症状匹配度 + 药效 + 价格 - 禁忌惩罚）
- 提供非 LLM 降级方案，确保系统在没有 LLM 时仍可运行

### 5.2 核心流程

```mermaid
flowchart TB
    A["用户输入症状描述"] --> B["症状标准化<br/>(symptom_service)"]
    B --> B1["查询 symptom_synonyms<br/>进行同义词扩展"]
    B1 --> B2["标准化为标准术语"]
    B2 --> C["药品匹配<br/>(screening_service)"]
    C --> C1["通过 drug_indications 表<br/>查询匹配药品"]
    C1 --> C2["计算症状覆盖度得分"]
    C2 --> C3["过滤禁忌症"]
    C3 --> D["药品排名<br/>(ranking_engine)"]
    D --> D1["症状匹配度权重 (40%)"]
    D --> D2["药品功效权重 (30%)"]
    D --> D3["价格优势权重 (20%)"]
    D --> D4["禁忌惩罚权重 (-10%)"]
    D1 --> E["结果输出"]
    D2 --> E
    D3 --> E
    D4 --> E
    E --> F["缓存"]
    F --> G["返回前端"]
```

### 5.3 排名算法

```
score(drug, symptoms) =
    w_symptom × match_score(drug, symptoms) +
    w_efficacy × efficacy_score(drug) +
    w_price × price_score(drug) +
    w_contraindication × contra_penalty(drug, patient_info)

标准权重: w_symptom=0.40, w_efficacy=0.30, w_price=0.20, w_contraindication=-0.10
```

### 5.4 缓存策略

| 缓存键 | 有效期 | 说明 |
|--------|--------|------|
| `drug_list` | 120s | 药品列表缓存 |
| `drug_stats` | 60s | 药品统计缓存 |
| `drug_detail:{id}` | 300s | 单品详情缓存 |
| `categories` | 300s | 分类缓存 |

## 6. 权限认证系统设计 (auth/)

### 6.1 设计目标

- 基于 JWT 的无状态认证
- 基于 RBAC 的细粒度权限控制
- 完整的操作审计日志

### 6.2 JWT 令牌设计

| 令牌类型 | 有效期 | 用途 |


### 7.5 优雅降级

当 ROS2 连接失败时：
1. `task_publisher` 进入重试模式（指数退避）
2. `state_subscriber` 标记为不可用
3. `health_monitor` 记录告警日志
4. API 层返回 `ros_connected: false` 但不影响其他业务
5. Web 前端显示 "ROS2 未连接" 提示

## 12. 安全设计

### 12.1 认证与授权

- **密码存储**：SHA-256 哈希（可通过配置升级为 bcrypt）
- **JWT 签名**：HS256 算法，密钥通过 `AUTH_JWT_SECRET` 配置
- **RBAC 权限**：基于数据库的动态权限检查，支持细粒度到端点级别

### 12.2 输入防护

- **SQL 注入防护**：全部使用参数化查询（`?` 占位符）
- **XSS 防护**：前端输出编码
- **CORS 配置**：通过 `CORS_ORIGINS` 限制跨域来源

### 12.3 审计日志

- 记录所有关键操作：用户 ID、操作类型、资源、IP、时间戳
- 审计日志持久化到 `auth_audit_logs` 表，支持查询和统计

## 13. 关键算法设计

### 13.1 药品匹配评分算法

```
score = symptom_coverage × 0.40 + efficacy × 0.30
        + (1 - price/max_price) × 0.20 - contraindication_penalty × 0.10

symptom_coverage = matched_symptoms / total_symptoms
efficacy = base_efficacy × age_factor × pregnancy_factor
contraindication_penalty = matched_contraindications / total_contraindications
```

### 13.2 症状同义词扩展

```
用户输入: "肚子疼"
    ↓ 查询 symptom_synonyms
标准化: "腹痛"
    ↓ 查询 drug_indications
匹配药品: [颠茄片, 藿香正气水, ...]
```

### 13.3 缓存淘汰策略

- **惰性淘汰**：读取时检查 TTL，过期则重新查询并更新缓存
- **定时淘汰**：后台线程每 60s 扫描一次，清理过期条目
- **写入淘汰**：药品数据变更时主动清除相关缓存

|------|------|----------|------|
| 数据库 | SQLite | PostgreSQL/MySQL | 零配置部署，单文件管理，适合桌面级场景 |
| 缓存 | 内存 TTL 缓存 | Redis | 避免额外依赖，内存开销可控 |
| 认证 | JWT + RBAC | Session/Casbin | 无状态、跨平台、细粒度权限控制 |
| LLM 供应商 | OpenAI 协议 | 仅单一供应商 | 兼容 DeepSeek/OpenAI 等多种模型 |
| 前端 | 原生 HTML/JS | React/Vue | 轻量、零构建步骤、快速迭代 |
| ROS2 通信 | ros_tcp_endpoint | ROS2 native | 统一 ROS-Unity TCP 通信协议 |
| 消息格式 | JSON | Protocol Buffers | 人类可读、调试方便、无需编译步骤 |
| ROS2 断开降级 | 状态标记 + 重试 | 硬依赖 | 保证 Web 业务不受机器人状态影响 |
| SQL 访问 | 参数化查询 | ORM (SQLAlchemy) | 轻量、零依赖、直接控制 SQL |

## 17. 质量属性场景 (Quality Attribute Scenarios)

定义关键质量属性及其验证场景：

### 17.1 性能 (Performance Efficiency)

| 场景 | 描述 | 当前基线 | 目标 |
|------|------|----------|------|
| API 响应时间 | GET /api/drugs 药品列表查询 | ~120ms (100 条) | P95 < 500ms |
| 药品筛选 | POST /api/screening/query 智能筛选 | ~800ms (含 LLM) | P95 < 2s |
| 静态页面加载 | Web 前端页面完整加载 | ~200ms | < 1s |
| 缓存命中率 | DrugCache 缓存药品列表命中率 | — | > 70% |

### 17.2 可用性 (Availability)

| 场景 | 应对策略 | 指标 |
|------|----------|------|
| LLM 服务不可用 | 降级为非 LLM 症状匹配（基于 symptom_synonyms 表） | 筛选系统仍可工作，准确率下降 |
| ROS2 节点断开 | task_publisher 指数退避重试，API 返回 ros_connected: false | Web 业务零影响 |
| 数据库文件损坏 | 定时备份策略（文档未实现，待补充） | RTO < 30min |
| 并发请求过载 | 线程池 + 请求排队（MAX_CONCURRENT_SESSIONS） | 拒绝超限请求而非崩溃 |

### 17.3 可修改性 (Modifiability)

| 变更场景 | 影响范围 | 耦合度分析 |
|----------|----------|-----------|
| 新增 LLM 供应商 | 仅修改 `llm/providers/` 目录，新增 Provider 子类 | 低 — 适配器模式 |
| 新增 API 端点 | 新增 controller 文件，注册 Blueprint，main.py 追加一行 | 低 — 独立注册 |
| 修改筛选算法 | 仅修改 `screening/services/ranking_engine.py` | 低 — 单一职责 |
| 替换数据库 | 需重写 `common/utils/database.py` 的 SQL 语句 | 中 — SQL 分散在各 controller |
| 修改 ROS2 消息格式 | 更新 `message_adapter.py` 转换逻辑 | 低 — 适配器隔离 |

### 17.4 安全性 (Security)

| 场景 | 防护措施 | 验证方式 |
|------|----------|----------|
| 未认证访问 API | `@require_auth` 装饰器守卫 | 401 返回测试 |
| 越权操作 | `@require_permission(code)` RBAC 检查 | 403 返回测试 |
| SQL 注入 | 全部参数化查询 `?` 占位符 | 渗透测试 |
| JWT 伪造 | HS256 签名 + 服务端密钥 | 篡改 token 签名后请求验证 |

## 18. 设计约束 (Design Constraints)

### 18.1 技术约束

| 约束 | 来源 | 影响 |
|------|------|------|
| 必须使用 SQLite | 部署环境限制（无独立数据库服务器） | 不支持并发写、不支持存储过程、数据量上限 ~TB 级 |
| 前端不可引入构建工具 | 团队前端技能栈限制（无 Node.js/npm 环境） | 使用原生 HTML/CSS/JS，无 SPA 框架 |
| ROS2 Humble | 机器人硬件支持的 ROS2 发行版 | 固件兼容性限制，升级需硬件配合 |
| Unity 2022.3.31f1 LTS | 仿真团队使用的 Unity 版本 | 项目文件不可用更高版本打开 |
| 同时支持 OpenAI 与 DeepSeek | 教学环境 API 供应不稳定 | 需要多供应商抽象层 |

### 18.2 业务约束

| 约束 | 说明 |
|------|------|
| 演示账号体系 | 预设 admin1/doctor1/patient1 三组演示账号，不可删除 |
| 药品数据固定 | 初始种子数据 116 种药品 + 599 条适应症为固定的演示数据集 |
| 审批流程强制 | 所有处方药品必须经过医生审批才能进入取药流程 |
| 单机部署 | 系统设计为单机部署模式，不涉及分布式协调 |

### 18.3 时间约束

- 项目周期：2026 年 3 月 10 日 — 2026 年 5 月 26 日（~10 周）
- Agent 核心优先策略：先验证 AI 问诊可行性 → 再拆分 5 组件并行开发
- Unity 仿真作为独立模块集成，不影响 Web 业务功能交付

## 19. 并发与同步策略

### 19.1 线程模型

```mermaid
flowchart TB
    subgraph Main[主线程 Flask]
        M1["Werkzeug 开发服务器<br/>单 worker"]
        M2["处理 HTTP 请求、响应<br/>每个请求在独立线程中处理"]
        M1 --> M2
    end

    subgraph ROS2[ROS2 后台线程 daemon]
        direction TB
        R1["task_publisher<br/>单线程循环"]
        R2["state_subscriber<br/>单线程循环"]
        R3["health_monitor<br/>每 30s 检测"]
    end

    subgraph Cache[缓存清理线程]
        C1["daemon<br/>每 60s"]
    end

    subgraph Expiry[库存过期扣减线程]
        E1["daemon<br/>每日"]
    end

    subgraph LLM[LLM 请求线程池]
        L1["MAX_CONCURRENT_SESSIONS<br/>默认 10"]
    end

    Main --> ROS2
    Main --> Cache
    Main --> Expiry
    Main --> LLM
```

### 19.2 锁策略

| 资源 | 锁机制 | 说明 |
|------|--------|------|
| `RosStateStore` 状态字典 | `threading.Lock` | 保护 car_states/task_states/cabinet_states 并发读写 |
| `DrugCache` 缓存 | `threading.Lock` | 保护缓存字典的读写 |
| 库存扣减 | 无锁（SQLite 事务保证） | 单机部署下无竞争条件 |
| 会话管理器 | `threading.Lock` | 保护多患者会话的并发存取 |

### 19.3 SQLite 并发限制

- SQLite 支持多读单写（WAL 模式下可并发读）
- 写操作串行化（文件级锁），高并发写入场景不适用
- 当前架构下，Flask 单 worker + SQLite 满足演示负载需求
- 写操作频率：~10 次/分钟（审批 + 订单 + 库存），远低于 SQLite 上限

### 19.4 Unity 仿真并发

- Unity 主循环（Game Loop）为单线程更新
- ROS 消息发送通过协程（Coroutine）按固定间隔执行
- 无多线程竞争，协程间共享 `TaskList`、`carQueue` 等资源
- `CarControl_2.StarTask()` 使用协程链实现顺序动画，无阻塞
