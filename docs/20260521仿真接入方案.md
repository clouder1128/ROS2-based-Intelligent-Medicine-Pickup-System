# 20260521 仿真接入方案

## 一、目标

将仿真全面接入当前项目，并使启动过程实现自动化：
- 后端与 ROS 节点运行在 Ubuntu 系统中；
- Unity 仿真运行在 Windows 系统中；
- Ubuntu 上运行的 ROS TCP 服务器与 Unity 端通过网络联通；
- `agent_with_backend/quick_start.sh` 自动启动 ROS TCP 服务、后端服务和前端静态服务器；
- 当前项目内新增顶层 `ros_workspace` 作为唯一标准 ROS 工作空间；
- 不修改 Windows 端 `unity_simulation` 的仿真逻辑；
- 不使用软链接，改为直接迁移代码和统一路径。

## 二、当前问题

### 2.1 现有 ROS 工作空间冲突

项目中存在两套 ROS 工作空间：
- 顶层参考目录 `ros-todo/ros_workspace`
- 外部参考目录 `newros_ws`

这两者都包含 `ROS-TCP-Endpoint` 和 `task_msgs`，会导致：
- 引用路径不一致；
- `PYTHONPATH` 和 `colcon build` 逻辑混乱；
- 启动脚本无法统一定位 ROS 工作空间；
- 运行时依赖不稳定。

### 2.2 `quick_start.sh` 未自动启动 ROS TCP Endpoint

现有 `agent_with_backend/quick_start.sh` 仅启动后端和前端，不启动 ROS TCP 服务器。
因此 Ubuntu 后端与 Windows Unity 之间的 ROS TCP 通信无法自动建立。

### 2.3 脚本路径仍指向旧工作空间

`agent_with_backend/scripts/setup/cli-patient-start.sh` 仍指向 `ros-todo/ros_workspace`，
应该统一改为当前项目顶层 `ros_workspace`。

## 三、方案概览

### 3.1 目标目录结构

```
ROS2-based-Intelligent-Medicine-Pickup-System/
├─ agent_with_backend/
│  ├─ quick_start.sh
│  ├─ scripts/setup/cli-patient-start.sh
│  ├─ main.py
│  └─ ros_integration/
├─ ros_workspace/
│  ├─ src/
│  │  ├─ ROS-TCP-Endpoint/
│  │  └─ task_msgs/
│  └─ install/  # build产物，可忽略提交
├─ unity_simulation/  # Windows Unity 端，不改动
└─ 20260521仿真接入方案.md
```

### 3.2 设计原则

- 只使用顶层 `ros_workspace` 作为运行时 ROS 工作空间；
- `newros_ws` 和 `ros-todo/ros_workspace` 只作为参考源，不作为正式依赖；
- 不采用软链接；
- 通过环境变量覆盖配置，并在脚本中提供默认值；
- `quick_start.sh` 负责自动检测 ROS 环境、构建工作空间、启动 ROS TCP endpoint；
- `cli-patient-start.sh` 负责从正确 ROS 工作空间加载 `task_msgs`。

## 四、ROS 工作空间迁移与构建

### 4.1 迁移内容

将 `newros_ws/src/ROS-TCP-Endpoint/` 和 `newros_ws/src/task_msgs/` 的源码迁移到本项目顶层：

- `ros_workspace/src/ROS-TCP-Endpoint/`
- `ros_workspace/src/task_msgs/`

保留 `package.xml`、`setup.py`、`launch/endpoint.py`、消息定义等所有源码文件。

### 4.2 构建流程

在项目根目录执行：

```bash
cd ROS2-based-Intelligent-Medicine-Pickup-System/ros_workspace
source /opt/ros/$ROS_DISTRO/setup.bash
colcon build --packages-select ros_tcp_endpoint task_msgs --symlink-install
source install/setup.bash
```

如果 `ROS_DISTRO` 未设置，可使用默认值：

```bash
export ROS_DISTRO=humble
```

### 4.3 构建结果验证

验证后端能导入 ROS 消息包：

```bash
python3 -c "from task_msgs.msg import Task, TaskState; print('ok')"
```

验证 ROS TCP endpoint 可启动：

```bash
ros2 launch ros_tcp_endpoint endpoint.py --ros-args -p ROS_IP:=0.0.0.0 -p ROS_TCP_PORT:=10000
```

## 五、脚本改造与自动化

### 5.1 `agent_with_backend/quick_start.sh` 改造目标

`quick_start.sh` 应该完成以下工作：

1. 检查 Python 依赖；
2. 检查并加载 `ros_workspace` 环境；
3. 自动构建 `ros_tcp_endpoint` 和 `task_msgs`（如果尚未构建）；
4. 启动 ROS TCP endpoint；
5. 启动后端；
6. 初始化数据库与演示数据；
7. 启动前端静态服务器；
8. Ctrl+C 时清理后端、前端和 ROS TCP endpoint。

### 5.2 具体改造步骤

- 新增变量：
  - `PROJECT_ROOT`：顶层项目路径；
  - `ROS_WS_PATH`：默认 `PROJECT_ROOT/ros_workspace`；
  - `ROS_WS_SETUP`：`ROS_WS_PATH/install/setup.bash`；
  - `ROS_DISTRO`：默认 `humble`；
  - `ROS_TCP_PORT`：默认 `10000`；
- 在 `cleanup()` 中增加：
  - 停止 ROS TCP endpoint 进程；
- 增加 ROS 环境检测逻辑：
  - 如果 `ROS_WS_SETUP` 存在，则：
    - `source /opt/ros/$ROS_DISTRO/setup.bash`
    - `source $ROS_WS_SETUP`
  - 如果 `ROS_WS_SETUP` 不存在，则：
    - 检查 `colcon` 是否可用；
    - 尝试构建 `ros_tcp_endpoint` 和 `task_msgs`；
    - 构建成功后再次 `source $ROS_WS_SETUP`。
- 增加启动 ROS TCP endpoint 的函数：
  - 使用 `ros2 launch ros_tcp_endpoint endpoint.py --ros-args -p ROS_IP:=0.0.0.0 -p ROS_TCP_PORT:=$ROS_TCP_PORT`；
  - 将 PID 保存在 `ROS_TCP_PID`；
  - 启动失败时调用 `cleanup()`。
- 将 `start_ros_tcp_endpoint` 调用放在后端启动前。

### 5.3 `agent_with_backend/scripts/setup/cli-patient-start.sh` 改造目标

`cli-patient-start.sh` 应该从顶层 `ros_workspace` 加载 ROS 环境，并将 `task_msgs` 的 Python 安装路径添加至 `PYTHONPATH`。

### 5.4 具体改造步骤

- 将 `ROS2_WS_PATH` 修改为：

```bash
export ROS2_WS_PATH="${ROS2_WS_PATH:-$PROJECT_ROOT/ros_workspace}"
```

- 如果 `ROS2_WS_PATH/install/setup.sh` 存在，则：
  - `source /opt/ros/$ROS_DISTRO/setup.bash`（可选）；
  - `source $ROS2_WS_PATH/install/setup.sh`；
  - `export PYTHONPATH="$ROS2_WS_PATH/install/task_msgs/lib/python3.12/site-packages:$PYTHONPATH"`；
- 如果目录或 `setup.sh` 不存在，则打印警告并提示用户执行：

```bash
cd $PROJECT_ROOT/ros_workspace
colcon build --packages-select ros_tcp_endpoint task_msgs --symlink-install
```

### 5.5 环境变量支持

推荐在项目根目录 `.env` 或 shell 环境中设置：

- `ROS_WS_PATH`：ROS 工作空间路径；
- `ROS_DISTRO`：ROS 发行版，例如 `humble`；
- `ROS_TCP_PORT`：ROS TCP 端口，默认 `10000`；
- `PHARMACY_BASE_URL`：后端 API 基地址；

## 六、运行验证

### 6.1 ROS TCP endpoint 验证

- `ss -tulpn | grep 10000`
- `ros2 node list` 中出现 `default_server_endpoint` 或相关节点

### 6.2 后端 ROS 状态验证

- `curl -s http://127.0.0.1:8001/api/ros/status`
- `curl -s http://127.0.0.1:8001/api/ros/task-states/<task_id>`

### 6.3 Unity 端验证

- Unity 成功连接 Ubuntu IP:10000；
- 能订阅 `/task_topic`；
- 能发布 `/TaskState_U`、`/CarState_U`、`/CabinetState_U`。

### 6.4 前端验证

- 患者页面正确轮询并显示任务状态；
- 管理员页面展示 ROS 小车和货柜状态；
- 如状态无法展示，优先检查 ROS TCP 连接、`task_msgs` 构建和字段兼容性。

- `unity_simulation` 目录仅作为外部仿真客户端存在，不在本方案中修改；
